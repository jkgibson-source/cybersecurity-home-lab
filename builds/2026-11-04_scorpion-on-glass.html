01The question that started it

TR1K3Y is a LILYGO T-Dongle-S3 — an ESP32-S3 the size of a thumb drive with a tiny 160×80 color LCD, running an open-source pentest firmware called LilyStrike. It talks to me over a little MCP server on its own Wi-Fi. It could already put text on its screen. The question JBird brought was simpler and better: could it make actual art?

The right way to answer that isn't to start flashing things. It's to design the thing first, and design it so you can watch it get better.

02Design as an art trail

The two original ASCII scorpions came first, followed by the denser ASCII version shown below. For the new pixel-art study, one pose was then carried through four comparable stages: ASCII → silhouette → shaded sprite → animation. These four design-study stages derive from the same pixel source. Their ASCII rendering is a reconstruction for comparison, not either of the original on-device ancestors.

The palette is deliberately small and built for a dark LCD: a warm amber body, a cold cyan rim that reads like a scorpion under UV, and a hot yellow spark at the stinger. Seven inks and a background.

03The wall — and a clue in the source

  
Then the catch: LilyStrike's documented screen commands covered backlight control, clearing, text, and live status. They did not expose bitmap loading or animation. The panel could draw graphics; the firmware needed a way for scripts to request them.

  
But the source left a tell. Buried in the script interpreter was a comment: SCREEN_IMG deferred. Someone had meant to add an image command and never finished it. That's not a dead end — that's an invitation.






  
04The smallest honest addition

  
The implementation described in Shade's session adds a function that streams RGB565 image data from the SD card in small chunks, plus two script verbs: one to show an image and one to loop frames. Streaming conserves working memory alongside LilyStrike's other tasks. A full 160×80 RGB565 buffer would take 25,600 bytes; the 96×58 sprite would take 11,136 bytes.

  
new file format — LSI1
  "LSI1" | u16 width | u16 height | width×height × RGB565  (little-endian)

new script verbs
  SCREEN_IMG  /scorpion/scorpion.lsi          one shaded frame, auto-centered
  SCREEN_ANIM /scorpion/f 4 220 0             loop 4 frames @ 220ms, forever






  
05The part the tinkerers will like

  
Getting there meant a string of very real, very ordinary gremlins — the kind that make a build feel earned.

  

    
    
      
  • A toolchain that wouldn't fitNo build tools installed, and PlatformIO's ESP32 stack is 5.8 GB — onto a Mac that was 93% full. So the whole toolchain got relocated to Bird's Nest, the lab's storage, reached through a space-free symlink so the compiler never chokes on the apostrophe in the volume name.
    • 
      
  • FS.h: no such fileA newer arduino-esp32 core broke the stock dependency wiring — the bundled USB library needed a header the build system wasn't handing it. One explicit include path, fixed.
    • 
      
  • A filename collision you can only hit on a MacThe project's own webserver.h and the framework's <WebServer.h> are different files on Linux, the same file on a case-insensitive Mac disk. The firmware pulled the wrong one and the web-server class vanished. A rename sorted it.
    • 
      
  • Flashed over the airShade reported installing the new firmware through the dongle's Wi-Fi OTA page, with scripts, settings, and autostart preserved. The claimed spare-slot and three-strike safe-mode behavior still needs checking against the saved firmware source.
    • 
      
  • The last-mile OOMShade reported upload failures while transferring approximately 25 KB frame files and attributed them to memory pressure. That diagnosis needs logs or source review to confirm. JBird spotted the practical workaround: flip on USB Mass Storage, mount the SD card as a plain drive, and drag the sprites straight on.
    •

06And now it's a scene

  
The loop is saved on the card as a replayable script, scorpion.ds. Run it manually, or add it to the autostart queue once the desired startup behavior is verified. Earlier testing found that autostart could depend on a USB host connection; power-only startup should be tested separately with this modified firmware. The whole trail — the art, the sprite data, the firmware diff — is kept, so the next idea starts from here instead of from scratch.

  
That's the part worth showing off. The photos and recording preserve the visible result, while the saved artwork and script provide a starting point for repeating it. Build details in this account come from Shade's session report; the exact diff, build size, and recovery behavior still need comparison with the retained source and logs.
