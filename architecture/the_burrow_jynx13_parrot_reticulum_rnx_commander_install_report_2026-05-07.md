# Troubleshooting Notes

## 1. Keep macOS and Parrot Identities Separate

Do not copy `~/.reticulum` between Jynx13 macOS and Jynx13 Parrot.

The separate identities are intentional:

```text
Jynx13 macOS:
ea05842d5394c202f240da1fba2c40c6

Jynx13 Parrot:
4783b00f2db6cae5f63594dc5d3f9c91
```

This allows the home listeners to trust both commanders while still preserving identity separation.

## 2. `rnx -l` Can Accept Multiple `-a` Flags

The session verified this working pattern:

```bash
rnx -l   -a ea05842d5394c202f240da1fba2c40c6   -a 4783b00f2db6cae5f63594dc5d3f9c91
```

This allows both the macOS and Parrot Jynx13 identities to command the same home listener.

## 3. `Serving : 1 program` Matters

For listener nodes, a healthy status should include:

```text
Shared Instance: Up
Serving: 1 program
TCPServerInterface: Up
```

Krypton1t3 briefly had:

```text
Serving: 0 programs
```

even though an `rnx -l` process appeared to be running. That state failed remote command execution.

Fix:

```bash
pkill -f "rnx -l" 2>/dev/null || true
pkill -f "rnsd" 2>/dev/null || true
```

## 4. AutoInterface Peer Count Is Not the Main Success Signal

For this Burrow Reticulum/RNX topology, the working path is TCP over Tailscale. Do not treat AutoInterface peer count as the primary success or failure marker.

Primary success markers:

```text
TCPInterface or TCPServerInterface: Up
Shared Instance: Up
Serving: 1 program on listener nodes
RNX command returns expected remote output
```

## 5. Use Shell-Wrapped Commands for Multi-Command Tests

Continue using shell-wrapped commands:

Linux targets:

```bash
"/bin/bash -lc 'hostname; date; uptime'"
```

macOS targets:

```zsh
"/bin/zsh -lc 'hostname; date; uptime; sw_vers'"
```

This avoids ambiguity in how `rnx` passes compound commands.
